# ADR-015 — A deterministic command may augment a consumer-supplied region list and stream its results, over a node-only tool set

- **Status**: Accepted
- **Date**: 2026-07-29
- **Realized by**: [augmentation.md](../interfaces/augmentation.md) FR-AU-01–FR-AU-34

## Context

Mythrix can retrieve ranked regions, narrow them by facet and by search text, and summarize one selected region. It cannot read the result set a user is looking at and report what those regions have in common — the research act the product exists to support.

The scope of that reading is the first question. A command could ask the user to describe what to analyze as a query, and retrieve its own regions. But the user has *already* said what they want examined: they ran a query, chose a source facet, chose an interpretant, and typed into the search box. Asking them to restate that as a second, differently-shaped query discards the selection they made and can return a different set of regions than the one on screen. The operand should be the display.

That operand lives in the consumer, and only in the consumer. The facet predicates, the search-box filter and the convergence/tie-break ordering are view logic; no server-side equivalent exists. Reproducing them in the backend would create two implementations of "what the user sees," free to drift, and cost a second retrieval to produce a list the consumer already holds.

The second question is delivery. Reading N regions is N+1 sequential generation calls, tens of seconds each against a local daemon. A response returned only on completion leaves the user with no indication of progress for a minute or more, and forces every per-region reading into one block of text rather than beside the region it describes.

There is also a quieter pressure, inherited. [ADR-012](adr-012-deterministic-command-nodes-bypass-tool-selection.md) established that a deterministic node fabricates the `AIMessage(tool_calls=…)`/`ToolMessage` pair a model-driven call would have produced, "so conversation history, the tool trace, and citation-marker accounting stay unchanged in shape." With `/summarize` that is two pairs. A run over eight regions performs eight passage reads and nine generation calls; fabricating all of it appends on the order of thirty-four messages, eight carrying full passages, into a thread the *next* ordinary turn replays into an 8192-token context (`generation_num_ctx`). One run would evict the rest of the conversation. ADR-012's rule was written for a two-call sequence and does not survive contact with a fan-out.

## Decision

**A command handled by a deterministic node may take its operand from the consumer's current display, fan out bounded generation over it, and stream the results back within its own turn.**

Concretely:

- **The consumer supplies identities; the backend derives everything else.** A turn carries the consumer's visible regions as an ordered list of region identities, separate from the context object. That list is authoritative for *which* regions and *in what order* — it already reflects whatever filtering and ordering the consumer applies, so no filter logic is duplicated server-side and no model participates in selecting or re-ordering a region. Every other attribute — source, human-readable locator, passage text — is derived by the backend from the identity alone, against its own stores. No displayed value the consumer sends is used, so the trust surface is one opaque coordinate per region, parsed and looked up.
- **The tool set splits by reachability.** `build_tools` returns a `ToolSet` with two lists. `model_tools` is bound to the orchestration model and is what `ToolNode` executes; `node_tools` is reachable only by name lookup from a deterministic node. Region reading and the augmentation/consolidation generation steps live in `node_tools`. The orchestration model has no binding for them, so the property holds by vocabulary rather than by prompt instruction: the operation does not exist in the model's tool schema.
- **A deterministic node may fan out N generation calls in one turn, bounded by its own configuration.** `agent_max_tool_iterations` (FR-AG-12) bounds the *orchestration model's* tool loop, which such a turn never enters; it is not a budget for work the backend decided to do. A fan-out therefore carries an explicit bound of its own (`augment_max_regions`), and the count of generation calls is arithmetic in that bound rather than a function of model behavior.
- **A node may record less in conversation history than it did work.** ADR-012's fabricate-every-pair rule is narrowed to: fabricate the pairs that citation-marker accounting needs, which is the record of augmented regions alone. The per-region passage reads and augmentations are observable in the process log, not in the thread. A fabricated tool result is rendered without passage text when the node read that text by structural coordinate anyway.
- **A turn is delivered as a sequence of events, not a single body.** The response is newline-delimited JSON ending in exactly one terminal event carrying the turn's context, reply text, instructions and thread-reset flag; an ordinary turn is that event alone. A long-running node may emit chat messages and instructions as it progresses. The run executes *inside* the turn, so the consolidation is the turn's own reply — in conversation history, subject to citation validation, and accounted for by the same marker machinery as any other reply.

## Consequences

- [ADR-010](adr-010-agnostic-adhoc-interpretant-query.md) is left intact rather than amended. Because this command retrieves nothing, [agnostic-query.md](../interfaces/agnostic-query.md)'s non-goal — the agent "cannot discuss, refer back to, or answer questions about a query run through this path" — remains literally true, and FR-CO-03 is satisfied vacuously: the command produces no query text at all. The free-text focus never reaches retrieval because retrieval is never reached.
- The consumer becomes a participant in what the backend analyses. This is a real coupling and is deliberately narrow: it supplies an ordered list of opaque identities and nothing else. A consumer that sends a region that does not exist gets it skipped, not honored.
- `POST /api/agent` no longer has a typed response body. `AgentTurnResponse` survives as the terminal event's payload model, but OpenAPI describes the response as a stream, and every consumer parses NDJSON even for a one-line reply. A non-streaming projection is kept as an internal drain for tests, never as a second endpoint — a published second contract would have to be kept equal to the terminal event, an invariant nothing enforces.
- Failures arising after a turn's first event cannot be transport-level errors. In practice this changes little: the turn service already caught `MythrixError` and returned a normal response carrying a failure message, and dependency construction still fails before the first event is written.
- The tool set is no longer a flat list, so `compile_agent_graph` takes a `ToolSet` and `api/dependencies.py` binds only `model_tools`. "Read-only is a structural property of this list" (FR-AG-04) becomes a property of both lists; neither contains a write operation.
- Conversation history after a run is small and lossy by design: the user's command, the record of augmented regions, and the consolidation. A later turn can refer back to the consolidation, but not to the raw passages or the individual augmentations, which were never in the thread. Reconstructing a run's full trace is a log operation.
- The per-turn cost of a run is bounded but large: N+1 sequential generation calls hold one HTTP connection open. There is no timeout anywhere in this codebase, so a hung daemon hangs the request. Streaming makes this visible to the user rather than fixing it.
- Citation markers gain a fourth kind. `[R#]` is validated like `[G#]`/`[S#]` but, unlike them, is **retained** in the delivered reply, because it is what lets a consolidated claim be traced to the region that supports it. Validation and stripping stop being the same predicate.
- [ADR-011](adr-011-backend-declared-agent-capabilities.md) is extended in one respect: an instruction may now be emitted mid-turn rather than only alongside a final reply. Its execution model is unchanged — a type declared with no binding is still handled in-app, and a consumer still implements result kinds rather than instruction types.

## Alternatives considered

- **Retrieve the regions server-side from a term list supplied with the command.** Rejected — it discards the facet, search and ordering choices the user already made, can return a different set than the one on screen, and reintroduces the ADR-010 exception (user text becoming query text) for a command that has no need of it.
- **Re-run the query server-side and re-apply the consumer's filters.** Rejected — the facet predicates, search-box filter and convergence/tie-break sort exist only as view logic; porting them to the backend creates two implementations of "what the user sees" with nothing keeping them equal, and costs a second retrieval to reproduce a list the consumer already holds.
- **Accept the consumer's full region records — source, locator, score, text — rather than identities alone.** Rejected — attribution and passage text would then be whatever the consumer sent, and a run's citations would no longer be backend-derived facts. Deriving from the identity costs one coordinate read per region and keeps the evidence trail intact.
- **Emit an instruction bound to a separate streaming endpoint, leaving `POST /api/agent` as plain JSON.** Rejected — the turn would end when the instruction is emitted, so the consolidation would arrive on a second connection and have to be injected into the thread out-of-band, placing it outside conversation history, outside citation validation, and outside marker accounting. It would also require reworking a binding vocabulary deliberately typed around one request yielding one result.
- **Return the whole run in one body, as the preceding design did.** Rejected — a minute or more of silence with no progress, and every per-region reading forced into one block of text rather than delivered beside the region it describes.
- **Extend each region's passage past its own span for additional context.** Rejected — the passage would no longer be what the region's locator and score describe, and adjacent regions could be handed overlapping text under different labels. Internal gaps are still filled, so a passage always reads as one contiguous sequence.
- **Fabricate the full tool trace into history, per ADR-012 unamended.** Rejected — an eight-region run would push roughly thirty-four messages including eight full passages into an 8192-token context, degrading every subsequent turn in the thread. Fidelity to a trace-shape convention is not worth poisoning the conversation it was meant to document.
- **Reuse `summarize_passage` for the per-region reading rather than adding a node-only augmentation tool.** Rejected — a passage read against a user's own question needs a prompt that names the question and instructs answering from the passage alone; giving that prompt to `summarize_passage` would change what a shipped `/summarize` returns (FR-AG-35). The two share the generation-call seam (`_generated`) and nothing else.
- **Augment regions concurrently.** Rejected for now — it would cut wall time roughly linearly, but the ordered progress stream is what makes a run legible (FR-AU-23, FR-AU-33), and wall time is not yet the binding constraint.
