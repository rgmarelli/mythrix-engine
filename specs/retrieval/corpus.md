# Ingestion + segmentation

How primary source documents enter the vector store and are broken into the atomic units that [Retrieval](retrieval.md) and [Ranking](ranking.md) operate over.

## Vocabulary

- **segment**: The atomic retrieval unit — one structurally-bounded piece of a source (e.g. a single scripture verse or numbered section), carrying exact structural coordinates and a stable ordinal position within its source.
- **structural coordinates**: The source-relative reference locating a segment (e.g. source id, chapter/section, verse/ordinal), sufficient to render a human-readable locator and to determine whether two segments are contiguous within the same source.

## Functional requirements

### Document ingestion

- FR-CO-01: The document loader ingests primary source texts, chunks them, embeds them via the local embedding model, and stores them with metadata sufficient to filter by domain and to reconstruct a human-readable citation (the source's citation label, locator). A document's `Source` carries no `Tradition` — it is identified by an explicitly authored id and a domain, both declared in the source's own structured-data file, colocated with the raw text it describes.
- FR-CO-02: Retrieval at query time always searches the full ingested document corpus — an uploaded document (e.g. a scriptural or literary text) is an independent corpus to be read *through* the graph's established symbolism, never scoped to a tradition, since a corpus document has no interpretive tradition of its own. This is distinct from comparing multiple *interpretive* traditions of the same sign against each other (e.g. Crowley's vs. Waite's reading of a card), which remains out of scope for v1 (see [domain-model.md](../domain/domain-model.md) Non-goals). An explicit scoping mechanism to keep a second interpretive tradition's commentary from blending into retrieval does not exist yet.
- FR-CO-03: The text used to drive similarity search is derived from retrieved graph facts — an interpretant's `value`, never a sign's or manifestation's `properties`, and never a sign's canonical name or a manifestation's denotation, and never raw, unvalidated user input. This includes the whole graph reachable from the queried sign via `intersemiotic_interpretants` ([domain-model.md](../domain/domain-model.md) FR-DM-03, [structured-data.md](../domain/structured-data.md) FR-SD-04) — each target sign's own interpretants are folded into the query too, but never the target's properties. An interpretant carrying a `query.directive: "filter"` annotation is excluded from the plain query text and is instead applied as an additional literal-text filter using its `query.as_token` value, alongside — never instead of — every other interpretant's plain query. An interpretant carrying a `query.directive: "skip"` annotation ([retrieval.md](retrieval.md) FR-RT-11) is excluded from retrieval entirely.
- FR-CO-04: The document loader computes a content hash of each ingested source file and records it on the corresponding `Source`. Re-running the loader with an unchanged file is a no-op (idempotent, no duplicate chunks); re-running with a changed file replaces that source's previously ingested chunks rather than accumulating stale ones alongside the new content.

### Segmentation

- FR-CO-05: The document loader segments a source along its own declared structure into atomic segments (one segment per smallest structural unit the source declares, e.g. a verse or a numbered section), rather than into fixed word-count windows, when the source declares a segmentation scheme; a source with no declared scheme falls back to fixed-size chunking. A segment never spans a structural boundary of its source, and no segment overlaps another.
- FR-CO-06: Each segment records exact structural coordinates and a stable ordinal position within its source, sufficient to (a) render a human-readable locator and (b) determine contiguity — whether one segment immediately follows another in the same source. Any structural-label prefix (e.g. a leading verse or section number) is excluded from the segment's matchable text so that it neither influences embedding nor produces spurious token containment.
- FR-CO-07: Segmentation is content-hash idempotent per source (FR-CO-04): re-ingesting an unchanged source is a no-op; re-ingesting a changed source replaces that source's segments.

### `chapter_section` scheme (ADR-020)

For a source whose only declared structure is chapter-level, with no per-paragraph numbering (chaptered prose, e.g. *The Golden Bough*):

- FR-CO-08: The document loader supports a `chapter_section` segmentation scheme. Under this scheme, the atomic segment is a single paragraph, taken verbatim, as in a source with no finer declared structure.
- FR-CO-09: A source declaring `chapter_section` declares its own chapter-heading pattern. A paragraph whose entire (stripped) text matches that pattern is a chapter heading, not a content segment: it marks the start of a new chapter, and every following paragraph belongs to that chapter until the next chapter-heading match. The pattern may additionally isolate the heading's descriptive title text from its own ordinal/marker via a named capture group; when it does not, the heading's whole matched text is used as the title (FR-CO-12).
- FR-CO-10: A source declaring `chapter_section` may additionally declare a subsection-heading pattern, matched the same way, one level finer than chapter. A chapter containing no subsection-heading match is treated as one implicit subsection spanning the whole chapter. A subsection's displayed ordinal is a single counter that runs monotonically across the whole source — it does not reset at a chapter boundary, even when the source's own subsection markers do.
- FR-CO-11: A source declaring `chapter_section` may declare a start and/or end occurrence-index boundary bracketing the region of the file containing its real chapters. A chapter-heading match outside a declared boundary (e.g. a table of contents or a per-chapter endnotes section reusing chapter-heading text) starts an excluded region: paragraphs are skipped until the next in-range chapter-heading match, if any.
- FR-CO-12: Each segment produced under `chapter_section` carries, as its structural coordinates, the ordinal and title of the chapter it falls within and, when the source declares a subsection pattern, the ordinal and title of the subsection within that chapter — the title text extracted verbatim from the source's own matched heading (FR-CO-09), before any display formatting. Unlike every other segmentation scheme, this raw text is not itself the segment's displayed locator — see Locator normalization below.
- FR-CO-13 (widens FR-CO-04): A source's content hash is computed from both its raw text file's bytes and its declared structure block (scheme and any scheme-specific fields, e.g. `chapter_pattern`). Changing only the structure declaration, with the raw text unchanged, is detected as a change: the previously ingested segments are replaced, never left stale alongside a declaration that no longer describes them.
- FR-CO-14: The document loader's dry-run preview reports, for a `chapter_section` source, the detected chapter breakdown (each chapter's label and how many segments fall under it) without embedding any segment or writing to the graph or vector store.
- FR-CO-15: A separate, store-free preview mode reports every one of a corpus source's segments together with its own displayed locator (computed exactly as a real query would render it — see Locator normalization), run directly against the source's raw text with no `Source` lookup, content-hash comparison, or graph/vector store handle opened at all — so it runs even while another process (e.g. a running API server) already holds the graph store's single-writer lock.

### Locator normalization

- FR-CO-16: For `chapter_section`, the displayed locator for a segment, or for a region spanning several segments, is computed at query/retrieval time from the raw chapter/subsection structural coordinates (FR-CO-12) — never stored pre-formatted at ingest. Title Case is applied to chapter/subsection title text regardless of the source's own casing (a source may mix ALL-CAPS and already-mixed-case headings within itself). "Chapter N"/"Section N" render abbreviated, as "Ch. N"/"§N". A region spanning more than one subsection within one chapter merges them into a grouped range ("§§M–N", with each side's title joined "First–Last"); a region spanning more than one chapter (rare) merges chapters the same way ("Chs. M–N"). This computation happens at exactly one point per retrieval path, so every consumer of a retrieved segment — the web viewer's region and reading panels, and the agent/LLM tools (`fetch_segments`, `query_sign`) — reads the identical formatted string.
- FR-CO-17: A chapter/subsection title is cleaned before display: a trailing period is stripped, and Gutenberg-transcription italics markup (`_word_`) is un-mangled to plain text (`word`). Scoped to title text only — never to a segment's own body text.
- FR-CO-18: A `numbered_section` source's (e.g. the Bahir) region locator merges two single-point section locators into a grouped range ("§83" + "§90" → "§§83–90") at the same query-time formatting point as FR-CO-16, rather than concatenating them as two separate citations. `scripture_verse` locators (e.g. the Bible) are unaffected by FR-CO-16–FR-CO-18.

## Reference corpus

`data/corpus/scripture/en_drb/` provides the complete Douay-Rheims Bible (Old and New Testament, public domain) as an independent corpus source — its `.yaml` (id, domain, citation label, bibliographic metadata) colocated with the raw `.txt` it describes, carrying no `Tradition` (FR-CO-01) — meant to be read *through* the tarot signs' established meanings rather than treated as their source. It declares a `scripture_verse` segmentation scheme (FR-CO-05), one segment per verse. `data/corpus/kabbalah/en_bahir/` provides the Sefer HaBahir as a second corpus source, declaring a `numbered_section` scheme, one segment per numbered section — proving segmentation is source-declared and corpus-agnostic, not scripture-specific.

`data/corpus/symbolism/en_goldenbough/`, `en_ritualromance/`, `en_primculture/`, and `en_secretteachings/` each declare the `chapter_section` scheme (FR-CO-08–FR-CO-15): Frazer's *The Golden Bough* and Hall's *The Secret Teachings of All Ages* additionally declare a subsection pattern (FR-CO-10); *From Ritual to Romance* declares a front/back-matter occurrence-index boundary (FR-CO-11), excluding a table of contents and a per-chapter endnotes section that both reuse its chapter-heading text.
